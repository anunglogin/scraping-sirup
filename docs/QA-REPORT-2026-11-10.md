### AC-07 — pengukuran sendiri (Python `urllib`, tanpa batas bawah 0,2 detik curl Windows; DB panas)

| Rangkaian | n | p50 | p95 | maks | > 1 detik |
|---|---|---|---|---|---|
| Campuran (benih 7, 3 putaran) | 261 | 0,150 | **0,859** | 1,78 | 8 (3,1%) |
| Campuran baru (benih 11) | 87 | 0,150 | **1,073** | 1,37 | 6 |
| Campuran baru (benih 23) | 87 | 0,124 | **1,013** | 1,25 | 5 |
| Satu filter saja (benih 101 + 202, tiap 52) | 104 | 0,10–0,11 | **0,34–0,39** | 0,91 | 0 |
| Gabungan 4 filter (benih 101 + 202, tiap 30) | 60 | 0,25–0,42 | **1,03–2,79** | 2,96 | 4 |

Kesimpulan: pencarian satu filter (pemakaian utama) jauh di bawah 1 detik. Campuran yang sengaja saya buat berat
(sepertiganya gabungan paket + satker + bulan + pagu) menghasilkan p95 antara 0,67 dan 1,07 detik tergantung
rangkaian; dari 338 permintaan "pertama kali" 15 (4,4%) lewat 1 detik, jadi 95,6% masih di bawah 1 detik, tipis.
Contoh lambat yang saya amati: `paket=komputer & satuan_kerja=badan & bulan=10,8,12 & pagu_min=1e7` → 714 ms
di database (EXPLAIN) tetapi 1,78 detik di API; ketiga indeks digabung (BitmapAnd). Sesudah restart database
(memori kosong) angka dari lead 1,1 detik — **tidak saya ukur ulang** (tidak me-restart sistem hidup).

## 3. Filter — cuplikan bukti (sistem hidup, sampel 100 baris, "tidak cocok" = baris yang melanggar filter)

```
paket=laptop            total=9324  tidak cocok=0      satker=puskesmas  total=10000 terbatas=True tidak cocok=0
paket=LAPTOP / LaPtOp   total=9324  tidak cocok=0      bulan=3           tidak cocok=0 (semua 'March 2026')
bulan=3,4 ; 3,3,3       tidak cocok=0                  pagu 100jt–1M     tidak cocok=0
pagu_max=0              total=66    tidak cocok=0      pagu_min=max=4jt  tidak cocok=0
paket+satker+bulan+pagu total=362   tidak cocok=0      paket+pagu_min    total=1571 tidak cocok=0
paket='100%'            total=530 (angka % ikut dicari apa adanya)       paket='a%c' total=0
```
Halaman: 5 halaman × 100 = 500 id unik, 0 ganda; `pagu_desc`/`pagu_asc` berurut; halaman 501×20 dan 101×100 → 422 dengan pesan;
`page=10^9` → 422 cepat; halaman di luar jangkauan (filter sempit, total 5, page 50) → `data: []`.
Validasi 422: kata kunci kosong/spasi/2 huruf/101 huruf, bulan 0/13/-1/huruf/kosong/1.5, pagu negatif/huruf/desimal/kosong/`1e3`,
min > max, `page`/`size`/`tahun`/`aktif`/`sort` salah. Detail: ID 0/-1/huruf/2^63 → 422; ID tidak ada → 404; ID benar → 200.
SQL injection (`'; DROP TABLE paket;--`, `' OR '1'='1`, `1; select pg_sleep(5)`, di `paket`, `satuan_kerja`, `sort`, `pagu_min`, path ID): semuanya 200 dengan 0 hasil atau 422; tabel utuh (3.638.698 baris sesudahnya).
