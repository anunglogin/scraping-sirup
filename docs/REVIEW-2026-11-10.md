## Ringkasan untuk bos

Sistemnya dibangun dengan rapi dan pada dasarnya aman: kata sandi dan kunci tidak bocor ke GitHub,
database tidak bisa dibuka dari luar, dan API menolak orang yang tidak punya kunci. Tapi saya menemukan
bahwa **cukup 10 pencarian "aneh" sekaligus (misalnya mengetik `...` atau `a..`) sudah membuat API mati
total sekitar 30 detik untuk semua orang**. Ini bisa terjadi karena salah ketik biasa, tidak perlu niat jahat.
Ada juga celah yang bisa membuat ribuan paket yang masih aktif **tersembunyi dari hasil pencarian selama sehari**
kalau SIRUP sedang bermasalah, padahal laporannya tetap tertulis "berhasil". Setelah dua hal itu diperbaiki
dan cara membuka API dari luar server dipastikan memakai HTTPS (gratis), sistem layak dinaikkan.

### Temuan Tinggi (wajib sebelum deploy)

#### F-01 — DoS murah: kata kunci tanpa trigram + pool kecil membuat API mati total (D2 diperluas, D3) — CACAT
- File: `src/sirup/api/main.py:84` (`SearchText = ... min_length=3, max_length=100`), `src/sirup/api/queries.py:68-73`, `src/sirup/api/config.py:19-20` (`db_pool_max_size=10`, `db_statement_timeout_ms=10_000`), `src/sirup/api/main.py:352-358` dan `:368-371`
- CWE-400 / CWE-770, OWASP API4:2023 (Unrestricted Resource Consumption); D3: CWE-20
- Risiko bagi bisnis: siapa pun yang punya kunci (termasuk karyawan yang salah ketik) bisa membuat API tidak bisa dipakai siapa pun.
- Penjelasan: `pg_trgm` hanya bisa memakai indeks bila kata kunci punya potongan huruf/angka yang cukup. Kata kunci seperti `...`, `%%%`, `___`, emoji, **dan juga `a..` / `e%%`** (satu huruf + tanda baca) membuat indeks trigram mengembalikan seluruh 3,6 juta baris, query habis 10 detik, lalu 503. Karena endpoint sinkron memegang 1 koneksi pool per permintaan dan pool maksimal 10, **10 permintaan serentak menghabiskan pool**: pencarian normal dan `/health` ikut 503 (bukti di atas). Ini lebih parah dari catatan QA (QA mencoba 6 serentak, masih di bawah ukuran pool). Pesan 503 "Database sedang tidak bisa dihubungi" juga menyesatkan (database sebenarnya sehat). Query tetap jalan sampai timeout walau klien sudah putus. D3: NUL di kata kunci lolos validasi dan menjadi `psycopg.DataError` lalu 503 + stack trace di log.
- Perbaikan:
  1. Validator `SearchText` (AfterValidator): tolak karakter kontrol (`\x00-\x1f`, `\x7f`) dengan 422 (menutup D3); wajibkan minimal satu potongan **>= 3 huruf/angka berurutan** (`re.search(r"[^\W_]{3}", value)`), selain itu 422 "Kata kunci harus mengandung minimal 3 huruf/angka berurutan". Berlaku untuk `paket` dan `satuan_kerja`.
  2. Turunkan `db_statement_timeout_ms` bawaan ke 3000 (target AC-07 < 1 detik; 10 detik tidak ada gunanya) dan teruskan `DB_STATEMENT_TIMEOUT_MS` lewat `docker-compose.yml`.
  3. Batasi pencarian berat serentak: `threading.BoundedSemaphore(N)` (mis. N = pool_max - 2) di dependency `/v1/paket`; bila penuh dalam 1 detik balas 429 + `Retry-After`. Sisakan koneksi untuk `/health` dan detail. Gratis.
  4. Tes integrasi: `paket=%%%`, `paket=a..`, `paket=<emoji x3>`, `paket=abc%00` harus 422 dalam < 1 detik.

#### F-02 — Halaman kosong di tengah run berakhir `success` dan bisa menonaktifkan paket yang masih hidup (D4 dinaikkan dari Rendah) — CACAT
- File: `src/sirup/scraper/runner.py:104` dan `src/sirup/scraper/store.py:66` + `:287-293`
  ```python
  if not page.data or next_start >= page.records_total:   # runner.py:104
      break                                               # -> finish_run(complete=True)
  if valid_received < MIN_COMPLETENESS * records_total:   # store.py:66 (99%)
  ```
- CWE-754 (penanganan kondisi tidak biasa yang salah)
- Risiko bagi bisnis: kalau SIRUP membalas halaman kosong di bagian akhir data, sampai **+-36.000 paket aktif** (1% dari 3,6 juta) ditandai "hilang" dan **disembunyikan dari pencarian bawaan** (`aktif=true`) sampai malam berikutnya, dan laporan run tetap "berhasil".
- Penjelasan: halaman `{"data": []}` sebelum `records_total` tercapai diperlakukan sebagai "selesai normal". Pengaman 99% hanya menolong bila potongan > 1%. Contoh: halaman terakhir (start 3.635.000) kosong: 3.635.000 valid >= 99%, maka `UPDATE paket SET is_active=false` mengenai +-3.900 paket yang tidak sempat dibaca. Untuk potongan > 1% penonaktifan memang dilewati, tetapi status tetap `success` dan `error` kosong (temuan QA).
- Perbaikan: bila `not page.data and start < page.records_total`, lempar `SirupUnavailableError("empty page at start=...")`. Paling rapi dilakukan di `SirupClient._fetch_once` (`client.py:131-142`) agar ikut retry tenacity; bila tetap kosong, run menjadi `failed` dengan checkpoint utuh untuk dilanjutkan. Tes: mode `emptymid` dan `emptylast` harus berakhir `failed`, `rows_deactivated=0`.

#### F-03 — Belum ada jalur akses aman dari luar VPS; RUNBOOK menyarankan membuka HTTP polos — CACAT (konfigurasi/dokumentasi)
- File: `docs/RUNBOOK.md:130` ("Untuk jaringan kantor: isi `API_BIND=0.0.0.0`"), `README.md:73`, `docker-compose.yml:100-101`
- CWE-319 (pengiriman kredensial tanpa enkripsi), OWASP API8:2023 (Security Misconfiguration)
- Risiko bagi bisnis: sistem ini dipasang di **VPS di internet**, bukan jaringan kantor. Mengikuti RUNBOOK berarti API + Swagger terbuka ke seluruh internet lewat HTTP polos; kunci API terkirim tanpa enkripsi dan bisa disadap. Docker juga melewati firewall `ufw` untuk port yang dipublikasikan.
- Penjelasan: bawaan `API_BIND=127.0.0.1` sudah benar. Tetapi pengguna pasti perlu mengakses dari luar VPS, dan compose tidak menyediakan reverse proxy TLS.
- Perbaikan (pilih satu, semuanya Rp0): (a) layanan `caddy:2.x` di `docker-compose.yml` dengan HTTPS otomatis (butuh subdomain), API tetap di jaringan internal; atau (b) akses lewat SSH tunnel (`ssh -L 8000:127.0.0.1:8000 <vps>`) / WireGuard. Ubah RUNBOOK §7 dan README: hapus saran `0.0.0.0` untuk VPS. **Wajib sebelum API dibuka ke luar VPS**; bila sementara hanya lewat SSH tunnel, cukup perbaiki dokumen.

### Temuan Sedang (perbaiki dalam sprint ini)

#### F-04 — Tidak ada pemberitahuan bila run malam atau backup gagal — SARAN (kesiapan produksi)
- File: `src/sirup/scraper/__main__.py:38-47` (setelah 3 kali coba ulang hanya log), `ops/backup.sh:33` (`BACKUP FAILED` hanya ke log)
- CWE-778 (pencatatan/peringatan tidak memadai)
- Risiko bagi bisnis: bos baru tahu data tidak diperbarui kalau ada yang mengeluh. AC-03 (paket baru <= 24 jam) bisa gagal diam-diam berhari-hari.
- Perbaikan termurah: "dead-man switch": di akhir run sukses dan backup sukses kirim ping HTTP ke Healthchecks.io (gratis sampai 20 cek), yang mengirim email/Telegram bila ping tidak datang sampai jam tertentu. Run `success` dengan `note` sebagian sebaiknya juga dilaporkan. Alternatif: bot Telegram (gratis).

#### F-05 — Offset paging bergeser selama run 52 menit, paket bisa terlewat lalu dinonaktifkan keliru — CACAT (dampak terbatas)
- File: `src/sirup/scraper/runner.py:68` dan `:85` (paging `start`/`length` urut `id`), `src/sirup/scraper/store.py:287-291`
  ```python
  "UPDATE paket SET is_active = false WHERE tahun_anggaran = %s AND is_active AND last_seen_at < %s"
  ```
- Risiko bagi bisnis: bila selama run ada paket ber-ID kecil dihapus di SIRUP, semua baris sesudahnya bergeser maju; beberapa paket di batas halaman tidak pernah terbaca dan ditandai "hilang" sampai malam berikutnya. `rows_received` bisa menghitung baris ganda, sehingga pengaman 99% kurang tajam. Hal sama terjadi saat melanjutkan dari checkpoint setelah jeda 30 menit.
- Perbaikan: nonaktifkan hanya paket yang tidak terlihat di **dua run lengkap berturut-turut** (`last_seen_at < started_at` run sukses-lengkap sebelumnya), atau ambil halaman tumpang-tindih (`start - 50`) dan hitung kelengkapan dari ID unik yang terlihat (`count(*) WHERE last_seen_at >= run.started_at`) bukan jumlah baris diterima.

#### F-06 — Scraper (pemroses data dari internet) memakai role superuser PostgreSQL — SARAN (pertahanan berlapis)
- File: `docker-compose.yml:82` (`DATABASE_URL: postgresql://${POSTGRES_USER}...`), bukti `sirup_admin | rolsuper t`
- CWE-250 (berjalan dengan hak berlebih)
- Penjelasan: saat ini tidak ada SQL injection, jadi bukan celah aktif. Tetapi jika suatu hari ada bug injection, superuser bisa `COPY ... TO PROGRAM` = menjalankan perintah di container database.
- Perbaikan: role `sirup_app` (bukan superuser) sebagai pemilik tabel untuk `migrate` dan `scraper`; superuser hanya untuk init/backup. Sesuaikan `ALTER DEFAULT PRIVILEGES FOR ROLE sirup_app`.

#### F-07 — Build tidak reprodusibel: dependency rentang longgar, base image mengambang — SARAN
- File: `pyproject.toml:10-21` (`fastapi>=0.115,<1`, `uvicorn[standard]>=0.30,<1`, dst.), `Dockerfile:2` (`FROM python:3.12-slim`), `Dockerfile:17` (`pip install .`), `docker-compose.yml:17,117` dan `.github/workflows/ci.yml:12` (`postgres:16`)
- CWE-1104, OWASP A06:2021 / A08:2021
- Risiko bagi bisnis: build ulang versi 0.1.0 bulan depan bisa menghasilkan program berbeda dari yang diuji QA hari ini; rollback lewat build ulang tidak menjamin hasil sama.
- Perbaikan: lock file berhash (`uv pip compile --generate-hashes` / `pip-tools`) dan `pip install --require-hashes -r requirements.lock` di Dockerfile; pin `python:3.12.x-slim@sha256:...` dan `postgres:16.14` (atau digest). Simpan image per versi (`docker save` / registry privat) agar rollback tidak bergantung pada build ulang. Tambah `pip-audit` di CI.

#### F-08 — Backup hanya di disk yang sama dengan database — SARAN
- File: `docker-compose.yml:128-130` (`./backups:/backups`), `docs/RUNBOOK.md` §5 ("Sebaiknya ... disalin ke tempat lain", manual)
- Risiko bagi bisnis: bila VPS rusak/terhapus, database dan semua backup hilang bersamaan. Data bisa diambil ulang dari SIRUP (+-52 menit), tapi riwayat `first_seen_at`, `is_active`, dan `scrape_runs` hilang.
- Perbaikan: `rclone copy` harian ke penyimpanan lain. Biaya: Backblaze B2 +-US$6/TB/bulan, untuk +-3 GB (7 x 430 MB) < US$0,02/bulan; atau Google Drive gratis. Gabungkan dengan ping F-04.

#### F-09 (D1, konfirmasi Sedang) — Pencarian gabungan beberapa filter teks 1–3 detik
- File: `src/sirup/api/queries.py:68-73`
- Setuju dengan QA: Sedang, bukan penahan rilis. Setelah F-01 (timeout 3 s + batas serentak) dampaknya ke pengguna lain terkendali. Optimasi lanjutan (lanjutan TD-06) dijadwalkan.

## Yang Sudah Bagus

- **SQL injection: tidak ditemukan.** Semua nilai pengguna lewat parameter terikat, nama kolom via `sql.Identifier`, ORDER BY lewat whitelist `Literal` + dict (`queries.py:10-17`), LIKE di-escape benar dengan `ESCAPE '\'` (`queries.py:48-50`), COPY memakai `copy.write_row`. Migrasi hanya SQL statis.
- **Autentikasi kunci API:** `secrets.compare_digest` ke semua kunci tanpa short-circuit (`main.py:94-96`), panjang minimal 24 dicek saat start, banyak kunci didukung (rotasi tanpa ganti kode), kunci tidak pernah dicatat di log, 401 seragam.
- **Database:** role API hanya `SELECT` di keempat tabel termasuk `paket_raw` (diverifikasi langsung), tidak bisa membuat objek di `public`, `default_transaction_read_only` + `statement_timeout` di level koneksi, port database tidak dipublikasikan, password role di `10-api-role.sh` di-quote dengan variabel psql.
- **Rahasia:** `.env` di `.gitignore` dan `.dockerignore`, `.env.example` lengkap, tidak ada rahasia di seluruh riwayat git, image tidak berisi `.env`.
- **Container:** API dan scraper berjalan sebagai uid 10001 (non-root), API terikat ke 127.0.0.1 secara bawaan, healthcheck db/api, `restart: unless-stopped`, rotasi log 10 MB x 5, migrasi sebagai layanan terpisah yang ditunggu.
- **Scraper sopan dan tangguh:** jeda 2 detik antarhalaman, backoff eksponensial 2–60 s, 429/5xx diulang, 4xx lain (403) tidak dipaksa, `follow_redirects=False`, advisory lock satu run, timeout 60 s, tidak ada upaya menembus pembatasan. Data SIRUP divalidasi pydantic dengan batas tipe kolom, NUL dibersihkan, > 50% baris rusak = gagal. Log contoh ID memakai repr list sehingga tidak bisa menyuntik baris log palsu.
- **Integritas data:** upsert `paket` + `paket_raw` dalam satu statement dan satu transaksi per halaman bersama checkpoint (atomik), deteksi perubahan berbasis `raw IS DISTINCT FROM`, `DISTINCT ON (id)` untuk ID ganda dalam satu halaman, pengaman penonaktifan berlapis. Live: 0 baris tanpa pasangan `paket_raw`.
- **Error handling API:** pesan ke pengguna generik tanpa stack trace, detail di log server; tidak ada CORS (browser dari situs lain ditolak).
- **Dependency & kualitas:** pip-audit bersih untuk `.venv` dan image yang berjalan; ruff bersih; 38 unit test lulus; setiap migrasi punya `downgrade` (0002 menolak downgrade bila akan merusak data).
- **Dokumentasi:** RUNBOOK lengkap (restore, uji restore, rollback dengan urutan downgrade yang benar, troubleshooting); README dan API.md sesuai perilaku kode kecuali catatan I-01/F-03.
